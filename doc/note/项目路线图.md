基于 Walnut 的现状，我们整理的问题如下：

现在 Walnut 主要的问题，不是快速开发的问题，而且安全性的问题：

# A: 安全问题

1. 会话机制应该升级为 `refershTicket/accessTicket` 机制以便获取最大安全性
   - 里面还有很多细节，譬如 HTTP Only Cookie 的问题
   - accessTicket 刷新的时机
   - 无论如何，我们需要一套让攻击者很难拿到会话票据机制

2. 每个请求机制应该加上签名和时间戳的保护
   - 签名防篡改
   - 时间戳防止重放

3. 用户通过 `/a/run` 提权的问题
   - 通过白名单，允许少量用户可以 `/a/run` 
   - 普通域用户只能 `/a/invoke/{name}` 对应到一个指定的 `jsbin`
   - 通过 `jsbin` 的包裹，可以自定义各种安全策略

4. 权鉴模型支持 `permission`
   - 原来的 `user-role` 基础上，每个 role 可以指定多个 `permission` 的键
   - permission 全集列表可以由域管理员指定
   - 标准IO对象，HTTP 接口, `jsbin`, SQL 模板 都可以通过 `permission` 限制访问
   - pvg assert 等问题也会被顺便重构掉

5. 机器人登录专用票据
   - 有限数量登录专票
   - 机器人权鉴后成功后，可凭此票据将会话提权

6. `mnt` 挂载和 `ln -s` 问题
   - 只有 `root` 权限系统账号才能挂载 `mnt`
   - `mnt-file-allow` 是系统配置属性，固定一个低级专用目录
   - 只有域主账户才能 `ln -s` 并且目标不能出域， `root` 不受限制

7. 密钥明文问题
   - 由于是动态多租户系统，密钥等信息很难通过环境变量注入，我们还得记录在数据库里
   - 各种外部访问的密钥，譬如 `.dao` 的数据库配置，不能直接 `cat` 出来
   - 标识这样的文件，为`受保护的对象`
   - 只有域主账户才能正常读写
   - 域子账户只读，在 cat, json,jsonx, `/o/read` 等地方明确截断输出
      - 需要 Io 提供一个保护性读取的接口
      - `cat/json/o/read` 需要使用该接口读取内容

8. History 审计问题
   - SQL 日志历史记录「已经基本解决」
   - HTTP API 日志，默认需要开启
   - 命令执行日志， 调用和细节需要梳理
   - 统一一个日志接口，打印系统日志，同时分流到日志存储队列

9. jsc 安全性问题
   - 建立真正的沙箱机制
   - 完全移除 groovy 的相关特性
   

# B: 工程问题

1. 移除 Nutz Mvc/Ioc 的依赖
2. 移除 WebSocket 相关支持
3. 切换到 `Jetty12` 同时支持 HTTP2
4. 修正 Admin 端口 stop 的问题（只能本机 127.0.0.1 才能发起）

# C: 功能问题

为了对智能体支持更友好，需要支持 MCP Server
