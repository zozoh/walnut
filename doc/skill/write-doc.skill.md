# 编写文档

> 任务：新增或修改 Walnut 的文档。先判断文档类型，再按对应结构写。
> Walnut 的文档分三类：**参考手册（reference）**、**技能文档（skill）**、**命令文档（command）**。

## 第 0 步：判断文档类型

- 讲**某个模块的机制原理**（它解决什么问题、怎么解决的）→ 参考手册，写到 `doc/reference/`
- 讲**怎么完成一类任务**（步骤、套路、踩坑）→ 技能文档，写到 `doc/skill/`
- 讲**一个命令怎么用**（简介、用法、示例）→ 命令文档，写到该命令源码旁的 `man/` 目录

一篇文档只干一件事，不要混型：参考手册里不要塞操作教程，技能文档里不要长篇讲机制原理
（机制细节用一句话 + 链接指向参考手册）。

## 一、参考手册（reference）

位置：`doc/reference/<两层次目录>/<name>.md`。目录结构见 `doc/reference/README.md`，
新文档必须挂进某个已有子目录，不要新建顶层目录（确有需要先与维护者讨论）。

### 结构模板

```markdown
---
title: 机制名称
module: 源码模块名（如 core.eot）
keywords: [关键词1, 关键词2, ...]   # 5~8 个，AI 检索就靠它
source:
  - 涉及的源码路径（相对 src/com/site0/walnut/）
related: [相关文档名, ...]          # 不带目录和后缀
---

# 机制名称

## 要解决的问题
（为什么需要这个机制：没有它会怎样，什么场景触发。一段话说清动机。）

## 解决思路
（核心设计：一两张 ASCII 图或流程清单，从入口到出口讲完数据怎么流动。
这是全文最重要的一节。）

## 重要细节
（边界行为、默认值、竞争与容错、常见误区。用无序列表，一项一条。）

## 主要代码类
（类名 + 一句话职责。无序列表，只列读源码时的入口类，不贴大段代码。）

## 扩展阅读
- [相关手册](相对路径.md) — 一句话说明为什么相关
```

### 写作要求

- 一切以 `src/` 源码为准。示例命令必须先在真实环境跑通或逐行核对过源码，
  **禁止从旧文档（`doc/_old/`）照抄**——那里面的内容很多已与源码脱节。
- 已弃用的功能不写入：`cmd_www`/站点模型、Thing 数据集、`/sys/noti`、
  `obj` 命令（用 `o` 代替）、微信支付实现。详见 `doc/note/00-项目总体认知.md`。
- 列表优先：内容长的对照关系一律用无序列表（`- **键**：说明`），
  只有每格 ≤ 20 字符的简单对照才允许用表格。
- 写完必须同步两处索引，否则等于没写：
  1. `doc/reference/INDEX.md` —— 在对应小节加一行
     `- **路径** — 标题 — 模块：x — 关键词：...`
  2. `doc/reference/SOURCEMAP.md` —— 涉及源码包「文档」列已有条目时改指向新文档

## 二、技能文档（skill）

位置：`doc/skill/<name>.skill.md`，命名用动宾短语（`write-cmd` 而非 `cmd-writing`）。
写完在 `doc/skill/README.md` 的编号列表里加一行。

### 定位与写法

技能文档是**任务驱动的套路沉淀**：假设 Agent 已经接到这个任务，目标是让它
读完就能干，并且每次实践后回来打磨文档，让套路越来越准。

结构建议（不强制，按任务性质裁剪）：

```markdown
# 做某事

> 一句话说明这个技能解决什么任务，什么情况下读这篇。

## 前置知识
（开始前必须已经知道的 2~3 个概念，每条一句话 + 参考手册链接。不要复制手册内容。）

## 步骤
1. 第一步（具体命令 / 文件路径 / 判断标准）
2. 第二步
3. ...

## 验收清单
- [ ] 怎么算做对了（可检查的判据，如「curl 返回 200」「man xxx 能看到新命令」）

## 常见坑
- 坑一：现象 → 原因 → 规避方法

## 套路沉淀
（实践中积累的技巧、好的参数组合、反面案例；做完一次任务后回来补充这一节）
```

### 写作要求

- **给路径不给搜索**：所有提到的文件、目录都写相对路径，Agent 不需要猜。
- 步骤里的命令必须是跑通过的；拿不准就先验证再写进来。
- 「套路沉淀」是技能文档与参考手册最大的区别：它随实践生长，
  鼓励在完成真实任务后回头补充，而不是一次写完美。
- 机制性内容一句话带过 + 链到 `doc/reference/`，保持技能文档轻量。

## 三、命令文档（command）

位置：**不是**写在 `doc/` 里，而是跟着命令源码走：

```
src/com/site0/walnut/<包路径>/man/zh_cn/cmd_<命令名>.md
```

铁律：**创建命令之前先写文档**。文档即设计稿——写不出简介和示例，
说明命令的边界还没想清楚。命令实现后再回来校对修订。

### 主命令文档（有子命令的，参考 `cmd_expl.md`）

复杂命令的主文档负责整体介绍，四块内容（参考
`src/com/site0/walnut/ext/data/expl/man/zh_cn/cmd_expl.md`）：

1. `# 命令简介` —— 一段话说清干什么；可以点出它调用的接口/服务
   （如「主要调用 `WnExplain` 接口」），让调用者知道能力边界。
2. **能力/语法分节** —— 按主题用 `##` 分节（如「支持的表达式语法」），
   每个语法点一个 ```` ```bash ```` 块，用注释说明行为。
3. `# 用法` —— 一个 ```` ```bash ```` 块给出完整调用形态。
4. **过滤器列表** —— 全部 `@子命令` 一行一个，行尾 `#` 注释一句话职责。

### 简单命令与子命令文档（参考 `cmd_expl_load.md`）

无子命令的简单命令、以及复杂命令的每个子命令，统一三件套（参考
`src/com/site0/walnut/ext/data/expl/man/zh_cn/cmd_expl_load.md`）：

````markdown
# 过滤器简介

`@load` 读取表达式内容

# 用法

```bash
expl @load
  [-f /path/to]      # 内容来自文件
  ["expression"]     # 表达式内容
```

# 示例

```bash
# 从文件里获得
expl @load -f ~/myexpl.txt
# 从参数里获得
expl @load '=var_name?default_value'
# 从管道获得
cat ~/myexpl.txt | expl @load
```
````

- 简单命令第一节标题用 `# 命令简介`，子命令用 `# 过滤器简介`；
  内容一律 ```` ```bash ```` 围栏块。
- 用法里选项逐行排列、行尾 `#` 注释说明，可选部分用方括号标出。
- 示例按输入来源/场景分组，每条上一行 `#` 注释说清干什么。
- 子命令文件名 `cmd_<主>_<子>.md`，对应 `man <主命令> <子命令>` 的
  查找路径（如 `man expl load` ↔ `cmd_expl_load.md`）。
- 旧文档（如 `cmd_echo.md`、`cmd_sqlx.md`）还是老式格式：4 空格缩进、
  `demo@~$` 提示符。**新写文档一律用本格式，不要模仿旧格式**；
  顺手维护旧命令时可以按本格式翻新。

### 写作要求

- 文档措辞面向**调用者**，不面向实现者：写「干什么、怎么调用」，不写
  「内部用了哪个类」。
- 示例命令必须真实跑通过；输出可选，写了就必须是真实输出，禁止编造。
- 新命令发布后，若属于重点命令（如 `o`/`sqlx`/`webx`/`mailx`/`tmpl`），
  还需在 `doc/reference/40.commands/` 检查专篇是否需要补充。

## 通用规范

- 全部中文；代码、命令、路径、元数据键用反引号或代码块。
- 示例是文档的灵魂：每个机制至少一个「从建到跑通」的完整例子。
- 修改文档时，与被改内容关联的索引（INDEX / SOURCEMAP / skill/README）
  一并更新，保持链接不断。

## 叙事风格

以 `doc/reference/10.concepts/01-std-obj.md` 为范本。核心是让读者**顺畅地读下去**：

- **活人感**：以 Walnut 作者的第一人称叙事（我/我们），像当面给读者讲自己的设计决策，
  不要写成中立的说明书腔。
- **从已知出发**：先锚定读者已懂的知识（最常用的是 `Linux/Unix` 文件系统类比：
  「你完全可以把 X 理解为 Y」），再逐步展开新信息。
- **不过早展开细节**：每写一段自问一句——读者（顺序阅读，只掌握前文）读到这里
  会不会恐慌困惑？会，就先铺垫或给比喻；还是不懂，就把细节挪走。
- **机制一句带过 + 链接深入**：概念篇只讲「是什么、能干什么、为什么省事」，
  完整机制（如 expi 的回收链路）用一句话 + 链接指向 reference 深入文档，
  绝不在概念里展开源码级细节。
- **一篇一个概念流**：按认知顺序分节（`# id 对象的标识` → `# nm 对象的名称` → …），
  每节一个小标题加一句白话副题，结尾用「总结」收束：
  「读到这里，关于 X 你应该没有什么更多需要知道的了」+ 一句话点出本质。
- **示例有真实感**：控制台示例带用户提示符和真实输出；命令必须跑通过。
- **诚实说明边界**：当前实现的限制要明说，未来可能的变化也预告
  （「后续版本可能对此做更严格检查，虽然现在你是可以的」），
  并一句话解释设计动机。
- **精简不等于丢失**：为流畅删掉细节时，把细节迁移到正确的文档
  （权限细节 → 30.auth，存储细节 → 20.io-storage，命令行为 → man 文档），
  并在原处留链接。
