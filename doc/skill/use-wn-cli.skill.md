# 用 wn-cli 操作 Walnut

> 任务：智能体在自动化测试（102.auto-test）中需要读写 Walnut 域里的数据。
> 核心原则一句话：**先查命令表，纯用命令；找不到命令就停下来和主人讨论，
> 不要自己写外围程序闷头乱试**——乱试既耗费 Token，又会把主人
> 注意不到的细节藏起来。

## 前置知识

- [自动化测试工具](../reference/102.auto-test/30-at-tools.md)：wn-cli 的子命令、
  会话缓存、退出码。
- [Walnut 命令机制](../reference/40.commands/README.md)：三种命令模式与管道；
  [命令总表](../reference/40.commands/60-cmd-table.md)：157 个命令的分类清单
  （73 内置 + 84 扩展），动手前先翻它。
- [Agent 测试守则](../reference/102.auto-test/50-at-rules.md)：异常即停、
  请示情形、汇报格式。

## 步骤

1. **先查命令，再动手**。打开命令总表按分类找
   （文件与对象 / 文本与数据 / 账户与系统 / data / net / sys …），
   或直接在命令通道里 `man <命令名>`。绝大多数"看目录、查对象、
   改元数据、灌数据"都有现成命令：

   ```bash
   # 看目录内容（最快，一眼看完）
   ls /app
   # 查对象完整元数据（含 mnt / md，结构化输出）
   o /app @query
   # 改元数据
   o /app/wn-hub @update 'mnt:"file://D:/work/proj/dist"'
   # 设置目录映射（wn-cli 的 mnt 子命令就是对它 + 自检的封装）
   mount /app/wn-hub file://D:/work/proj/dist
   ```

2. **用命令通道，不写外围程序**。`wn-cli cmd '<命令文本>'` 的语义与
   控制台完全一致，输出本身就是结构化的（`@json`、`textTable` 等）。
   不要在 wn-cli 外面再写 Python/shell 程序去拼装"查询 + 解析输出"——
   多一层外围程序就多一个出错环节，而且把操作过程藏进了代码里，
   主人看不到你实际做了什么。命令文本本身就是最好的留痕。
3. **REST（obj 子命令）只留给文件字节**。大文件上传下载才用
   `obj upload/content`；结构化操作一律走 cmd。
   （obj 系列端点还有一些怪癖，比如尾斜杠报 noexists，
   agent 场景没理由去碰。）
4. **找不到命令 = 停下来讨论**。想做的事在命令表里没有对应物时，
   不要自己绕路（写临时脚本直连数据库、手工拼 HTTP 请求）。
   先向主人说明"我想做 X，查了命令表没有找到"，一起讨论：
   也许是姿势不对，也许该把它固化成新工具——
   固化路径是 `.at/_ottl/` 一次性脚本 →  Walnut 仓库 `bin/` 公共工具。

## 验收清单

- [ ] 动手前翻过命令总表或 `man`，确认用的是现成命令（或确认没有）
- [ ] 含 `~` 或以 `/` 开头的路径参数都加了引号（防本地 bash 展开/转换）
- [ ] 完成任务只用了 `wn-cli cmd` 的命令文本，没有写外围解析程序
- [ ] 找不到命令时停下来请示了主人，而不是自行绕过

## 服务端日志在哪看

排查问题的第一手证据。日志时间戳是 **UTC**（格式 `yyMMddTHH:mm:ss`，
比本地慢 8 小时），按时间对号时先换算。

- **级别 2（dist 产物实例）**：
  - 业务日志在 `<walnut仓库>/.at/walnut/log/`，按需取用：
    - `access.log`——每个 HTTP 请求一行：身份、状态、耗时、
      **解码后的真实参数**。客户端到底发了什么，以它为准；
    - `cmd.log`——命令通道里每条命令的执行记录；
    - `core.log` / `sql.log` / `box.log` / `bgt*.log`——内核、SQL、
      box、后台任务（cron/schedule/task）。
  - 启动的 stdout/stderr 在 `dist/wn4j/run/walnut-<port>.log|.err`——
    启动失败先看它（start.cmd 自己失败时也会打印它的尾部）。
- **级别 3（自己 `.at` 的私有化实例）**：同样的文件布局，在自己工作
  目录的 `.at/walnut/log/`（`log4j2.xml` 的 `@LOG_DIR@` 构建时注入）。
- **级别 1（开发者 IDE 实例）**：日志在 IDE 控制台，属于开发者本人，
  不要去翻；需要时向主人描述现象，请主人帮忙看。
- 实时跟踪（Windows 没有 `tail -f`）：`tail-watch.cmd <日志文件>`
  （主人已装在 `D:\opt\_bin`，支持通配符与 `-n` 行数）。

排查顺序：`access.log` 确认客户端实际发出的参数 → `cmd.log` 看命令
执行 → `core.log` 看异常堆栈。

## 常见坑

- **Git Bash 会吃掉对象路径**：形如 `/app` 的参数被 MSYS 自动转成
  `C:/Program Files/Git/app` 再传给 wn-cli，服务端报
  `e.io.obj.noexists`——看起来就像"对象不存在"，极具迷惑性
  （2026-11 真实案例：`obj get /app` 全线 noexists，命令通道却一切
  正常，查了半天服务端源码才定位到调用环境）。对策：
  `export MSYS2_ARG_CONV_EXCL='*'`，且路径参数一律加引号。
  wn-cli 已有客户端防线：路径参数出现盘符开头或 `/c/...` 挂载形式、
  或命令文本里出现落在 MSYS 根目录下的盘符片段，会直接报错并提示
  上述对策，不再把脏路径发到服务端。
- **裸 `~` 比路径转换更阴险**：`MSYS2_ARG_CONV_EXCL` 只管路径转换，
  管不了 bash 自己的波浪号展开——`obj get ~/tmp`（没加引号）会被本地
  bash 先展开成 `/c/Users/<name>/tmp` 再传给 wn-cli（2026-11 真实案例：
  因此把 `save-text` 的 forbidden 误诊为"REST 身份评估问题"，白做
  一串 chmod 探测；而同一会话的 cmd 通道因为命令文本整体在引号里
  完全正常）。所以引号不是建议，是纪律：**凡是含 `~` 或 `/` 开头的
  路径参数，必须加引号**。
- **行为诡异先对服务端日志，别凭空构建理论**：`access.log` 里有
  解码后的真实请求参数（如 `/o/get?str=/c/Users/DELL/tmp`），一眼
  就能看出客户端到底发了什么。理论和日志冲突时，永远信日志。
  （日志位置见上文"服务端日志在哪看"。）
- **写含复杂引号的文件，别走 echo 过命令通道**：命令文本要穿过
  本地 bash 和 box 两层引号解析，`{nm:"..."}` 这种内容会被啃得
  引号全无、语义尽失（2026-11 实测：regapi 命令模板被剥成
  `{ nm : ${http-qs-nm} }`）。box 的单引号还不保护反引号
  （`` ` `` 会触发命令替换）。**这类内容一律走字节通道**：
  本地写好文件，`obj save-text --file` 或 `obj upload` 推上去，
  分毫不差。echo 重定向只适合单引号、反引号、反斜杠都不含的
  简单文本。
- **regapi 模板变量缺参数时原样保留**：`${http-qs-nm}` 在参数没传时
  不替换，占位符原文进入命令（接口收到的 nm 就是字符串
  `${http-qs-nm}`）。显式给默认值：`${http-qs-nm?}`。
- **`&&` 连接符在命令通道里行为异常**：多条命令分开多次传。
- **`~` 由客户端展开**：服务端会把 `~` 解到服务器 OS 的 HOME，
  wn-cli 在客户端展开成 `/home/<usr>`（root 是 `/root`）。
  写命令文本时放心用 `~`，但别指望服务端展开。
- **报错读不出端倪 = 异常**：既不像成功也不像明确的失败时，按守则
  停下来汇报，附上原始输出，不要重试到底。

## 套路沉淀

- 查证类操作的默认两件套：`ls <目录>`（快速看内容）+
  `o <路径> @query`（看完整元数据）。比 obj 子命令的 REST 通道
  又快又直观。
- 每条命令文本都是现成的汇报素材：出问题停下来时，把命令原文 +
  原始输出一起贴给主人，对照手册第几步说明停在哪。
- 域内 HTTP 接口的标准形态（2026-11 实测打磨）：API 文件只做一行
  命令模板转发 `jsc ~/jsbin/xxx.js -vars '{nm:"${http-qs-nm?}"}'`，
  业务逻辑全在 jsbin 脚本里（ES5！）——白名单校验、存在性/类型/
  尺寸检查、try/catch 兜底都写在那；API 元数据开
  `http-dynamic-header:true`，脚本按 `HTTP/1.1 <code>\nHeader\n\nbody`
  格式输出，就能精确控制状态码（400/404/413/500 各归各位）。
- 元数据修改用 `o <路径> @update 'k:v'`；`-u` 是已弃用 `obj` 命令的
  参数，`o` 对不认识的参数**静默忽略**——命令正常返回但什么都没
  发生，是文档里 cmd_obj 时代残留写法的重灾区。
