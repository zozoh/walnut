# 定时任务概述

一个业务系统总会有定时执行一些业务逻辑的需求，
`Walnut` 因此为你构建了一个可以精确到分钟的业务逻辑定时执行的系统。

首先，通过命令机制，我们可以把任何业务逻辑描述在一个命令里。
> 很多时候，甚至绝大多数时候，通过 `jsc` 命令以及一个自定义的 `js` 业务脚本
> 我们可以解决绝大多数问题
然后我们面临的唯一问题，就是如何定时调用它。

描述启动时间点，这个通过 `cron` 表达式很容易做到。`Walnut` 也有一个自己内置的
`cron` 命令实现, 你可以通过 `man cron` 查看详细语法。

总之它会把你要执行的命令存入一个对象，这个对象统一放在 `/sys/cron/` 目录下
是一个系统级的目录，用户只能通过 `cron` 命令来操作。它会保证你只能维护自己的定时任务。
当然 `root` 用户可以管理所有的定时任务

这个命令的细节，可以参见 「cron-task.md」

之后系统会有一个线程，每隔一段时间（通常是5分钟）会统计系统所有的定时任务。
把接下来几分钟要执行的任务，统一写入 `/sys/schedule` 目录下。
这个操作抹平了 `cron` 表达式的复杂性，无论你怎么指定 `cron` 表达式，
都会被展开成一个个分钟槽，合并到 `/sys/schedule` 目录下。

接着另外一个线程，每分钟会启动一次，它会从 `/sys/schedule` 目录下取出任务，统一放到一个系统
后台任务队列里 `sys/tasks/`。

最后一个执行线程，会尽快从 `sys/tasks/` 目录下取出任务，放入执行线程池，
**为每个任务启动一个执行线程，以任务里声明的 user 身份运行命令**。

> ⚠️ 当前实现里，线程池的方案还在源码中被注释掉，每个任务实际是 `new` 一个
> 独立线程来执行（执行完再 `join` 回收）。源码的注释里标记了 TODO，
> 计划在未来改用虚拟线程。这个细节对使用者透明，这里只是如实说明现状。

## 全景图

把上面的叙述画成一张图，整条流水线是这样的：

```text
 cron add
    │
    ▼
┌─────────────┐   BGT_CRON 预加载线程（默认预载 5 个槽）
│ /sys/cron/  │ ───────────────────────────────────────────▶
│ cron_task   │      展开 cron 表达式 → 分钟槽
└─────────────┘
                     │
                     ▼
┌────────────────┐   BGT_SCHEDULE 推送线程（每分钟一次）
│ /sys/schedule/ │ ────────────────────────────────────▶
│ 分钟槽         │      当前槽的任务 → 任务栈，并删除该槽
└────────────────┘
                     │
                     ▼
┌──────────────┐   BGT_TASK 消费线程（尽快）
│ /sys/tasks/  │ ────────────────────────────▶
│ 后台任务栈   │      批量弹出 → 每任务一个执行线程
└──────────────┘                        │
                                        ▼
                              以任务 user 身份执行命令
```

三个后台线程（`BGT_CRON` / `BGT_SCHEDULE` / `BGT_TASK`）都在系统启动时
由 `WnSetup` 统一拉起。前两个受配置项 `sys-schedule-enabled` 控制（默认开启），
`BGT_TASK` 则总是启动——因为任务栈不只服务定时任务，任何模块都可以往里放任务。

## 为什么要拆成三张表

看完全景图你可能会问：既然最后都是执行命令，为什么不能一个目录搞定？

- **`/sys/cron/` 存「定义」， `/sys/schedule/` 存「展开结果」**。
  把一个 `cron` 表达式展开成分钟槽是昂贵的操作，不应该每分钟都算一遍。
  预加载线程每隔几分钟批量展开一次，把未来几个槽的计划写好，
  推送线程每分钟只需要做一次廉价的「取出当前槽」。
- **`/sys/schedule/` 和 `/sys/tasks/` 解耦「何时」与「如何执行」**。
  分钟槽只负责说「这一分钟该跑哪些任务」，任务栈负责执行。
  这样任务栈可以被复用：其他模块投递的后台作业、`task add` 手动补跑，
  最终都是往同一个 `/sys/tasks/` 里放任务，由同一个消费线程执行。
- **三张表都是普通对象目录**。你可以用 `o` 命令直接查看它们的结构和内容，
  调试调度问题时非常直观。

## 相关配置

- `sys-schedule-enabled`：是否启用定时调度（`BGT_CRON` + `BGT_SCHEDULE`），
  默认 `true`；如果你的节点只消费任务不调度，可以关掉。
- `sys-cron-preload-amount`：预加载线程每次向前展开多少个分钟槽，默认 `5`。
- 多节点部署时，`load/push` 和任务弹出都需要分布式锁
  （IoC 中的 `sys-schedule-lockdu` / `sys-schedule-task-lockdu` 配置锁时长），
  请确保锁服务是 Redis 实现，否则任务会被重复执行。

## 可靠性与注意事项

- **调度精度是 1 分钟**。秒级的需求请考虑用消息队列，或者自己轮询。
- **任务是弹出即删除**。任务从 `/sys/tasks/` 弹出后就消失了，
  如果执行过程中进程崩溃，这个任务不会自动重试
  （源码里留有 TODO，考虑为失败的任务增加重试机制）。
  因此命令模板应该是幂等的，或者自己能容忍偶尔丢一次。
- **任务以 `user` 身份执行**。写命令模板时要考虑该用户的 HOME 目录、
  权限和配额，不要假设它是 root。
- **避免长时间阻塞**。命令模板里如果有外部调用，记得给 `httpc` 等命令
  设置好超时。
