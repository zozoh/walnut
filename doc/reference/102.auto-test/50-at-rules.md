# Agent 测试守则概述

## 要解决的问题

工具再顺手，也替代不了判断力。这套测试环境是人和智能体一起用出来的：
智能体越是谨慎地停下来问，环境规则就能打磨得越准；
反之，绕过异常硬往前冲，会把脏数据、误停的服务留给下一个人。

**总原则只有一条：任何不符合预期的现象，立即停止当前任务，向主人汇报。
不许自行绕过、不许重试到底、不许装作没看见。**

下面按场景展开。

## 异常处理

- **先自检，再相信**：挂载目录后 `ls` 看内容是否符合预期；写入数据后
  读回来核对；命令输出与手册描述不符时，以实际输出为准并报告偏差。
- **看不懂就是异常**：输出读不出端倪（既不像成功也不像明确的失败），
  按异常处理——停止，汇报，附上原始输出。
- **服务器行为突变**：昨天能登录今天 401、探针时通时不通、响应格式
  与契约不符——这些都可能意味着别人正在动这个实例。停止，汇报。
- 唯一的例外是**已知的瞬时故障**（如启动等待超时重试），且手册里
  明确写了重试策略。清单之外，不重试。

## 登录与凭据

- 密码登录失败累计 **3 次，终止测试流程并警告用户**。不猜密码、
  不遍历、不尝试"常见的默认密码"。
- 凭据只从工作目录的测试信息文件读取；该文件不进 git。
- 票据（session ticket）是会话的身份，**不贴进日志、不发到外部、
  不写进会提交的文件**。缓存只在 `.at/client/session/`。
- root 凭据只在"建域"这一个场景使用；用完不驻留内存流程之外的任何地方。

## 实例生命周期

- **只停止自己启动的实例**。发现端口被占且探针确认是 Walnut——
  那是别人的（很可能是开发者 IDE 里的调试实例），复用，绝不停止。
- wn-down 因"找不到运行锁"或 `started_by` 不符而拒绝时，这是设计
  行为，不是工具故障。向主人说明情况即可。
- 自己启动的实例，任务结束可以停止（级别 2/3）；但如果手册说
  "保留给同伴 Agent 用"，就留着，并在汇报里说明它还在跑。

## 数据与协作

- 多个 Agent **可以共用同一个测试域**（分模块测试、测协同）——
  手册会写明同域的其他 Agent（看各自的 `whoami.json` 代号）在测什么。
  动公共数据前先读，写操作尽量限定在自己模块的数据范围。
- 不删数据目录来"重置"。清表、删数据对象即可；垃圾目录留着无妨。
- **模式固化**：发现自己第三次手写同一段数据准备代码，停下来向主人
  建议固化成工具（`.at/_ottl/` 的一次性脚本 → Walnut 仓库 `bin/` 的
  公共工具，晋升路径见 [工作目录测试准备](40-at-project.md)）。这是让环境越来越好用
  的正循环。

## 需要请示用户的情形

以下情形给默认值也必须请示，不许自作主张：

- 级别 3 私有配置的 `mnt-file-allow` 白名单（给多大范围）。
- 构建 dist 或自建级别 3 配置时，`build.rs.json` 里的数据库连接
  信息（mongo/redis/mysql 落在哪个库）——必须向用户确认后才能用。
- 要停止一个 `started_by` 不是自己的实例（哪怕看起来没人用）。
- 要在共享域里删除或改动**其他模块**的数据。
- 测试信息文件缺失或字段不全（不要编造，直接问）。

## 汇报格式

停下来汇报时，一次性给全：

```text
【停在哪】正在执行的任务步骤（对照手册第几步）
【看到什么】原始输出/错误码/探针结果，原样贴出
【试过什么】已做过的确认动作（如自检、重登一次）
【建议】你认为合理的下一步，等主人拍板
```

## 重要细节

- 守则是手册的一部分：ATEST.md 可以收紧（更严格），不可以放松
  （更宽松）。收紧的例子："本项目的公共数据一律只读"。
- 守则本身随实践生长——每次"停下来汇报"的case，都值得回来琢磨
  是守则没说清，还是工具该提供更好的判据。
