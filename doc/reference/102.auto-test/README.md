# 自动化测试概述

## 要解决的问题

越来越多的项目由智能体（Agent）开发：它们写前端、写脚本，需要 Walnut 作为后台
来跑通自己的测试。但 Walnut 对它们来说有一层门槛——要先构建、启动服务、
登录、给自己开一个测试域、再学会读写域里的数据。这些步骤对人类开发者是
"搭环境"，对智能体却是每一步都可能卡住的未知领域。

**我们的答案是：不教智能体零散的命令，而是给它一套约定。** 约定好目录放哪、
工具叫什么、每个工具的输入输出是什么，智能体读一遍手册就能自己跑完全程，
中途任何一步出现异常，它应该停下来问人，而不是瞎试。

这套约定同样适用于人类开发者——它本来就是从人类的开发习惯里长出来的。

## 解决思路：三件套

整个方案由三件套组成：

```text
一套目录约定   每个 Agent 工作目录长一个样子（.at/ 目录），
               手册、配置、会话、数据各就其位
一组小工具     Walnut 仓库 bin/ 下的 Python 脚本：探测、启停、客户端、
               脚手架——所有智能体共享同一份，一个脚本一个目录，
               JSON 输出，可被程序解析
一篇手册       每个项目工作目录里的 ATEST.md，声明本项目用哪级 Walnut、
               测试域叫什么、数据怎么准备
```

智能体的典型工作流长这样：

```text
读 ATEST.md → wn-ping 探活
  ├─ 活着 → 直接用（共享实例，永不替人停止）
  └─ 没活着 → 按手册级别启动（wn-up）→ 等探针就绪
登录测试域 → 不行 → root 登录 → adduser 建域 → 再登录
wn-cli 读写数据（命令通道 + ObjModule + mount + sqlx）
测试 → 不停止共享实例，走人
```

## 三级启动模型

智能体面对的服务实例分三级，用哪一级由项目手册声明：

- **级别 1 —— 共享开发者的实例**：8080 已被占用且探针确认是 Walnut，
  直接复用。可能是开发者 IDE 里跑的调试实例。**铁律：绝不停止它。**
- **级别 2 —— 独立实例 + 构建默认配置**：用构建产物（dist/wn4j）的默认
  配置启动，数据落在构建默认位置（由 `build/build.rs.json` 指定的
  mongo/redis 库，见 [构建 Walnut 测试服务](10-at-build.md)）。大多数 Agent 自助场景走这一级。
- **级别 3 —— 独立实例 + 私有配置**：在工作目录 `.at/walnut/conf/` 里
  自建 `web_local.properties`（独立端口、独立 mongo 库、私有数据目录、
  自己的 mnt-file-allow 白名单），启动时把 conf 目录传给启动脚本，
  它会优先于构建默认配置被加载。只有需要完全隔离时才用这一级。

## 全局原则（速览）

完整版在 [Agent 测试守则](50-at-rules.md)，这里先立四条最重要的：

- **任何不符合预期的现象，立即停止并汇报主人**，不自行绕过。
  这套环境是靠这个原则一点点打磨光滑的。
- 密码登录失败累计 3 次，终止测试流程并警告用户。
- 只停止自己启动的实例。
- 发现自己在反复做同一个数据操作模式，主动建议主人把它固化成工具。
