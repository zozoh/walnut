# HTTP 注册接口（regapi）

## 它解决什么问题

让一个域的用户**不写 Java、不部署应用，就能搭出自己的动态 HTTP 服务**：
动态网站的数据接口、App 的后端、向第三方开放的数据 API。

如果没有这个机制，你要提供一个 HTTP 接口，就得写代码、打包、部署、运维。
regapi 的思路是把这件事压缩成「在树上放一个文件」。

## 设计的初衷：把「统一」延伸到 HTTP

Walnut 的目标是用**统一的方式写任意业务代码**：一切皆对象，
业务逻辑无非是读写对象、执行命令。到了 HTTP API 这里，自然也想延续这个统一——

**读取请求信息就是读文件，返回响应信息就是写输出。**

于是就有了这个机制里最核心的两个决定：

- 一个 API 是**文件**：内容是一段命令模板，定义了接口的行为；
- 一次请求也是**文件**：请求到来时临时创建，Query String、Header、Cookie
  是它的元数据，请求体是它的内容，用完即弃。

你的命令模板面对的上下文，与平时操作任何对象时没有区别。
不需要学新的编程模型——`cat`、`grep`、`o`、`sqlx` 会什么，接口就会什么。

## 两种对象，两种角色

regapi 涉及两种对象，角色完全不同，先分清它们，后面的文档才读得顺：

- **API 接口对象**——`~/.regapi/api/` 下的一个文件，**定义了一个 API**。
  它长久存在：内容是命令模板，元数据决定这个接口的行为
  （鉴权、缓存、输出……）。如何定义它，是 10-api-object 的主题。
- **临时请求对象**——每次 HTTP 请求在 `~/.regapi/tmp/` 下临时创建的对象，
  **描述了这一请求**：Query String、Header、Cookie 都是它的元数据，
  请求体就是它的内容。用完由过期机制自动回收。
  命令模板里的 `${http-qs-xxx}` 占位符，引用的就是它。
  它能提供什么，是 20-request-object 的主题。

## 核心思路：文件即接口

```bash
HTTP 请求  /api/{域}/{路径...}
    │
    ▼
路由到 ~/.regapi/api/ 下的一个文件 ── 找不到 → 404
    │
    ▼
为本次请求创建一个「请求对象」── HTTP 的一切信息变成它的元数据和内容
    │
    ▼
以文件所有者的身份，执行文件内容（命令模板）
    │
    ▼
命令的标准输出 = HTTP 响应体
```

三个要点：

- **一个文件就是一个 API**。文件的内容是命令模板，模板的占位符上下文就是本次请求的请求对象（见上文两种对象）。
- **请求被对象化**。请求体就是对象的内容，Query String 就是对象的元数据——
  你平时怎么操作对象，就怎么处理请求。
- **安全是内生的**。API 以文件所有者的身份执行命令——
  这就是「命令即 API」的权限根基，接口能做什么，取决于文件放在谁的目录里。

## 一次请求的完整旅程

上面流程图里的每一步，在源码中对应一条明确的处理链。把散落在各专题文档里的
校验、注入、缓存串起来，一次请求的实际经过是：

1. **路由**：按 URL 路径逐层定位 API 对象，未命中时尝试 `_ANY` 通配（30-path-params），
   找不到 → 404；
2. **预检**：OPTIONS 跨域预检请求直接按跨域配置返回；
   随后填充请求元数据——URL、Query String、Header、Cookie、会话信息都进元数据；
3. **令牌**：`api-access-token` 校验，失败返回 403；
4. **参数转义**：`http-safe-params`（默认开）对 Query String 参数做防注入过滤；
5. **站点会话**：按票据恢复站点会话，注入 `http-www-me-*`；
   声明了 `http-www-auth` 却没有会话 → 403；
6. **预加载**：`preload` 按条件执行命令，结果并入上下文；
7. **缓存**：`cache-test` 命中且未过期 → 直接返回缓存（或 302），后续步骤全部跳过；
8. **权限断言**：存在站点会话时，`pvg-setup` / `pvg-assert` 检查角色与动作，
   不通过 → 403；
9. **生成请求对象**：创建临时对象，写入全部元数据与请求体——
   命令模板面对的「当前目录」就是这里；
10. **执行**：以 API 文件所有者的身份执行命令模板或 JS；
11. **响应**：命令的标准输出即响应体；
12. **历史**：`_record_history` 写历史记录（当前实现为 TODO，见 50-auth-history）。

这张顺序表也是阅读后面专题文档的地图：
每篇专题文档讲的，都是这条链路上某一个环节的细节。

## 行为全靠元数据

文件放好后，接口的行为——鉴权、跨域、缓存、重定向、响应头、站点登录、
历史记录——全部通过在 API 文件上声明元数据来配置，不需要改任何代码。
元数据以 `http-`、`cache-` 等前缀分组，覆盖访问控制、参数处理、输出控制等方方面面。

这套元数据的全集，以及请求对象里能拿到哪些上下文，分别在两篇专题文档里。

## 专题文档

- 20-request-object：请求对象——每次请求你能拿到什么

## 总结

读到这里，regapi 的本质就一句话：**把 HTTP 请求对象化，把接口文件化，
让命令模型直接长出 Web 能力**。它没有引入新的编程模型——
一切都是你已经认识的对象、命令与会话。
