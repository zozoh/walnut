# 账号认证机制概述

## 基本思路：一切都是对象

既然 一切皆对象，账号体系也不例外：

- **用户**是一个对象（`/sys/usr/xiaobai`），密码、手机、角色都是它的元数据
- **会话**是一个对象（`/var/session/${TICKET}`），过期机制自动回收
- **权限**长在对象自己身上（`m` 权限位 + `pvg` 元数据），随对象移动、随对象删除

没有独立的账户数据库表、没有独立的 Session 服务器——`WnLoginApi`（登录接口）
只是对这组对象的标准操作：查用户、验密码、建会话、查角色。
读懂了对象模型，认证体系就没有秘密。

## 三种存储模式

`WnLoginApiMaker`（`login/WnLoginApiMaker.java`）是登录接口的工厂，按用户群体
提供三种组装方式，差异只在「用户和角色存哪、会话存哪」：

- **`for_sys` — 标准账户会话模式**：用户/角色是系统对象（`/sys/usr/`、`/sys/grp/`），
  会话进 `/var/session/`。Walnut 系统本身的登录（控制台、管理界面）就是它。
  详见 系统用户、角色与密码存储 与 会话管理
- **`for_domain` — 域内用户会话模式**：用户/角色存进**站点自己的目录**
  （由站点配置指定，标准对象存储或 SQL 映射表），会话独立管理。
  面向「站点自己的用户库」——你的 App 的用户，不是 Walnut 的用户。
  详见 域内用户存储与认证
- **`for_hydrate` — 混合模式**：会话强制用系统会话存储，用户/角色用站点配置。
  效果是：**域内用户登录后拿到一个标准的系统会话**，可以像系统用户一样
  进入域主目录操作。详见 混合认证机制

三种模式共用同一套 `WnLoginApi` 接口——调用方（命令、regapi、过滤器）不需要知道
自己面对的是哪种模式。

## 对象权限体系：动机

数据放在对象上，权限也就地解决，不需要独立的 ACL 服务：

- `m` 权限位（三段八进制）解决「这组数据谁能看、谁能改」
- `pvg` 元数据解决「例外授权」——把某个目录开放给特定伙伴
- 更细的「角色能不能做某动作」（如「运营能不能审核文章」）由业务权限矩阵负责

详见 标准对象的权限体系。

## 验证码与 OTP

登录前后的辅助认证有两道，各自独立成服务：**人机验证码 captcha** 挡机器人，
**动态密码 OTP**（短信/邮箱）确认「本人持有这个手机号/邮箱」。
OTP 存 Redis（前缀按场景区分），**一个账号同一时刻只能进行一种验证**。
详见 动态密码 OTP 与 人机验证码 captcha。

# 总结

读到这里，账号认证的地图就清楚了：

```bash
用户/角色/会话 都是对象
        │
三种组装模式（WnLoginApiMaker）：sys / domain / hydrate
        │
登录后：会话对象记下你的身份与环境变量，之后的请求凭票据找回这个会话
访问时：权限就长在数据自己身上（m + pvg），在每个对象上拦截越权
```

一句话：认证体系没有引入任何独立于对象模型之外的东西——
账户是对象、会话是对象、权限是对象的元数据。
所有的机制，都是在对象模型的基础上做组合。

按需深入：

- 会话管理
- 域内用户存储与认证
- 混合认证机制
- 标准对象的权限体系
- 动态密码 OTP
- 人机验证码 captcha
